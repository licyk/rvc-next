The Web UI is a Vue 3 project under `rvc_next/webui/` and also a Python package: its git-ignored `dist/` build is bundled as package data in the wheel and served by the API's `SPAStaticFiles` (see [API and events](/docs/development-api)). It has no business logic of its own—REST is the sole data source, and socket events only keep the cache fresh.

The skeleton (theme, `ui/` components, motion, rule tests, API client, and socket wrapper) comes from Hanaikada, which inherited it from SD Model Hub; RVC Next adds audio components (waveforms, level meters, device menus, parameter sliders) and five feature screens. This page covers the stack, directories, shared components and unified experience contract, data flow, layout and motion rules, internationalization, tests, and steps for adding a screen.

Charts and waveforms use no third-party libraries: server-computed peaks are drawn on canvas (`ui/Waveform.vue`), loss curves use `ui/LineChart.vue`, and level meters and progress bars use ordinary elements with CSS transforms.

Scripts in `package.json`: `dev` (Vite), `build` (`vue-tsc --noEmit` then `vite build`), `build:only`, `typecheck`, `test` (`vitest run`). For daily use, call them through `scripts/dev.py`: `web-install`, `web`, `web-dev`, `test-web` (tests + type checking), `dev` (API and Vite together, with Vite hot module replacement); see [Development environment](/docs/development-setup).

### Development proxy

[`vite.config.ts`](https://github.com/licyk/rvc-next/blob/main/rvc_next/webui/vite.config.ts) proxies `/api`, `/openapi.json`, and `/ws` (WebSocket) to `RVC_NEXT_BACKEND` (default `http://127.0.0.1:7868`), so the browser sees only Vite's origin and needs no CORS. During development, the API process is often restarted after Python changes (it does not reload automatically; restart it manually), and the socket reconnects every few seconds. For backend-unavailable errors such as `ECONNREFUSED` and `ECONNRESET`, the proxy prints one throttled message (at most every 5 seconds) and returns 502 JSON (`code: "api_unreachable"`) for HTTP requests instead of leaving the browser waiting. Other errors are printed in full as usual. `isExpectedProxyError` is tested by `devProxy.test.ts`.

`vite.config.ts` also declares tags starting with `md-` as custom elements, maps the `@` alias to `src/`, and inlines `@material/material-color-utilities` in tests (version 0.4.0 has an extensionless import that plain Node cannot resolve).

## `ui/`: the design system layer

`src/ui/` is the only place that imports `@material/web` and `@lucide/vue` (with additional test patches in `test/setup.ts`); views and feature components import only from `@/ui` ([`ui/index.ts`](https://github.com/licyk/rvc-next/blob/main/rvc_next/webui/src/ui/index.ts)). This layer isolates risk: `@material/web` no longer adds components, so if one fails in a browser, it can be replaced in `ui/` without changing application code. Icons are re-exported through `ui/icons.ts` and rendered with `<AppIcon :icon="icons.X" />`.

There are two kinds of components:

- **Wrappers around `md-*` elements**: `AppButton`, `IconButton`, `Fab`, `Checkbox`, `Switch`, `Slider`, `TextField`, `Tabs`, `SegmentedButton` (also exported as `SegmentedControl`), `FilterChip`, `Divider`, `ProgressCircle`, `ProgressBar` (only its indeterminate form), `ParamSlider`. They define props, event names, and types, without layering extra animation over the built-in `md-*` animation.
- **Custom components** (missing from or unsuitable in `@material/web`): `AppShell`, `NavigationRail`, `NavigationBar`, `TopAppBar`, `AppCard`, `Surface`, `AppDialog`, `ConfirmDialog`, `SideSheet`, `Snackbar`, `Tooltip`, `AppMenu`, `ContextMenu`, `SelectField`, `DeviceMenu`, `SearchField`, `TokenField`, `PathField`, `DataList`, `Breadcrumbs`, `Stepper`, `ExpansionPanel`, `EmptyState`, `Skeleton`, `Badge`, `Chip`, `KeyHint`, `DropZone`, `Waveform`, `LineChart`, `LevelMeter`, `PageFooter`.

Several mechanisms span components:

- `useLayer`: dialogs, side sheets, and menus are stacked in opening order; `Escape` closes only the top layer.
- `reveal.ts` (`revealDropdown`, `useRevealWhileOpen`): if an inline dropdown (voice picker, device menu) is hidden by the sticky `PageFooter`, scroll the container upward until it is visible, without passing the list's top. `PageFooter` marks itself with `data-page-footer`.
- `useSnackbar`: a global queue, showing one message at a time.

### Theme and tokens

- [`theme/scheme.ts`](https://github.com/licyk/rvc-next/blob/main/rvc_next/webui/src/theme/scheme.ts): `DEFAULT_SOURCE_COLOR = '#3f5f90'` is the project's only hand-picked color (the logo blue); `SOURCE_COLORS` supplies the alternatives in Settings. `generateScheme()` uses `SchemeTonalSpot` to generate every role in `ROLES`, supporting light/dark and contrast values 0, 0.5, and 1.
- `theme/applyTheme.ts` writes roles to `--md-sys-color-*` on `:root`; `watchSystemTheme` reacts to system changes in “System” mode. The inline script in `index.html` sets `data-theme` before the bundle loads to avoid an initial flash.
- `theme/tokens.css`: MD3 tokens for fonts, shapes, heights, motion, state layers (hover 8%, focus 12%, pressed 12%, dragged 16%), and project `--app-*` tokens: spacing `--app-space-*`, widths `--app-width-*` (all `clamp()`, growing with wider screens), stacking `--app-z-*`, disabled opacity, etc. Some tokens (such as `--app-z-viewer`) are inherited from Hanaikada and currently unused.
- `theme/breakpoints.ts`: MD3 window size classes (600, 840, 1200, 1600 px). `AppShell` uses bottom navigation in compact mode (&lt; 600 px), otherwise a navigation rail.

Rules: components and views use tokens rather than literal colors, corner radii, font sizes, or durations (colors are enforced by `tokens.test.ts`); pair color roles (`on-primary` on `primary`); express hierarchy through surface tones first, shadows second.

### Motion

Motion follows MD3's four patterns. Named transitions are centralized in [`ui/motion/motion.css`](https://github.com/licyk/rvc-next/blob/main/rvc_next/webui/src/ui/motion/motion.css) and `TRANSITIONS` in `ui/motion/transitions.ts`; views use `<Transition :name="TRANSITIONS.x">` instead of defining their own transitions. The principle is that every visible change is animated, with faster exits using an acceleration curve.

| Name | Purpose | Actual use |
| --- | --- | --- |
| `fade-through` | Switching between unrelated states | Destination-switching fallback without View Transitions |
| `shared-axis-x` | Peer tabs or steps; direction set by `--axis-dir` | Models tabs, Settings sections, the experiment's four steps; `useAxisDirection()` computes direction synchronously when the value changes |
| `container` | A card grows into a dialog | `AppDialog` and `ModelDetailView` compute the initial transform with `containerFrom(from, to)`; without a source rectangle, fall back to a scaled fade-in |
| `sheet` / `scrim` | A side sheet slides in from an edge | `SideSheet` (Jobs sheet) |
| `list` | Adding, removing, and reordering items (`TransitionGroup`) | Results, job cards, voice grids; `staggerStyle(i)` offsets each item by 20 ms, up to 12 items |
| `collapse` | Expand/collapse, height set by `collapseHooks` | `ExpansionPanel`, `JobCard` |
| `snackbar` | Bottom notification | `Snackbar` |

**Destination changes use the View Transitions API.** When the browser supports `document.startViewTransition`, `installViewTransitions(router)` in [`ui/motion/viewTransition.ts`](https://github.com/licyk/rvc-next/blob/main/rvc_next/webui/src/ui/motion/viewTransition.ts) wraps navigation across destinations (`to.name !== from.name`) in a view transition; navigation within a destination is not wrapped. Key points:

- The browser pauses rendering during the update callback, including `requestAnimationFrame`, so the callback must finish on Vue's `nextTick` (when the new view is in the DOM), never wait for a frame—an early frame-based wait froze navigation.
- When a new navigation interrupts an unfinished transition, finish the old one first; rejected Promises from skipped transitions are all caught.
- When supported, `App.vue` renders views directly without `<Transition>`; otherwise it falls back to `<Transition mode="out-in">` with `fade-through`.

**The shell stays still.** Only the scroller `main.content` has `view-transition-name: app-content`; `motion.css` disables animation on the root snapshot, so navigation, indicators, and the top bar update in place while only page content fades out and in. The rounded background `.frame` belongs to the shell, outside the snapshot. Previously, the entire document root participated, so the entering `scale(0.92)` scaled the rail and top bar too.

**Reduced motion.** With system `prefers-reduced-motion: reduce` or “Reduced” in Settings (`<html data-motion="reduced">`): all transitions become 100 ms linear fades without translation or scaling; view transitions become 100 ms crossfades without scaling; ripples are hidden; CSS animations become instantaneous. Destination changes still use view transitions under reduced motion—a short crossfade rather than a hard cut, because accessibility concerns movement, and abrupt jumps can also be uncomfortable. `prefersReducedMotion()` checks both sources.

**High-frequency values.** Determinate `ProgressBar` bars are drawn directly: `md-linear-progress` restarts a 250 ms ease-in-out on every update, making values that change several times per second (Live load, uploads, jobs) stutter; the custom bar catches up to new values with an ease-out curve. `LevelMeter` moves with `transform` (no layout on each update), following audio-meter ballistics: fast rise, slow fall, with the peak tick falling slowest; `useFalling()` tracks the previous direction of change. `LiveStatsBar` bars glide smoothly between 10 Hz statistics.

## Unified experience contract

Shared components make every feature feel part of one application; use them as the review checklist for each screen (AGENTS.md §7).

| `VoiceParamsPanel` | The single parameter panel: identical labels, ranges, defaults, help, and order everywhere. A few more conventions:

- **Screen hand-offs** (“Use as input”, “Convert this”, “Try”, “Re-run with these settings”) go through `stores/handoff.ts`: the sender calls `sendInputs(screen, items)` / `sendVoice(id, params)`, and the receiving screen consumes them with `take…()` when opened. They are not passed through URLs, avoiding paths or parameters in the address bar.
- **Imports**: every drop zone on Models (Voices, Base models, Separation models) calls `components/useModelImport.ts`: create a session, upload each file with progress, read the plan; commit immediately if `plan.confident`, otherwise pass the plan to `ImportReviewDialog`, where each index lists only compatible candidate voices plus “Keep unassigned”. Unassigned indexes appear in `IndexInbox` on Voices.
- **Consistent terminology**: `i18n.test.ts` checks fixed terms (Voice and its Chinese equivalent, Index strength, Consonant protection, Loudness match), and ensures the original's inconsistent terms (retrieved feature ratio, loudness factor, `rms_mix_rate`) never appear in copy.

## Data flow

<Mermaid chart={"flowchart LR\n    REST[\"REST /api/v1\"] -->|\"useQuery / useMutation\"| QC[\"TanStack Query cache<br/>(keys.ts)\"]\n    SOCK[\"socket.io events\"] -->|\"setQueryData / batched invalidation\"| QC\n    SOCK -->|\"job_updated · live_stats · train_metrics\"| ST[\"Pinia stores<br/>jobs · live · train\"]\n    QC --> V[\"Views and components\"]\n    ST --> V\n    V -->|\"Mutations\"| REST"} />

- **REST is the sole source of truth.** `api = createClient<paths>({ baseUrl: BASE_URL })` in `api/client.ts` has middleware that adds `Authorization: Bearer` when a token exists and sets `useAuthStore().needed` on 401, opening `AuthDialog`. `unwrap()` converts `openapi-fetch` results into data or `ApiError(status, code, message, detail)`; `ApiError.missingAssets` reads `detail.assets` from `asset_missing`. Uploads use `uploadRaw()` (`XMLHttpRequest`, with progress); `urls` builds media URLs, and `<audio>` authenticates through the `rvc_next_token` cookie.
- **Queries**: `api/queries/<resource>.ts` wraps `useQuery`/`useMutation`; all keys live in `keys.ts`, shared with socket handlers. Successful mutations invalidate affected keys; job-starting mutations write the returned `Job` to the jobs store and record the originating screen (`jobs.upsert(job, 'convert')`).
- **Socket** ([`api/socket.ts`](https://github.com/licyk/rvc-next/blob/main/rvc_next/webui/src/api/socket.ts)): connect once at `${BASE_PATH}/ws/socket.io`, supplying the token in the handshake `auth` callback. Events either write directly to the cache (`assets_changed`, `live_state`, `devices_changed`, `compute_changed` carry full snapshots) or batch invalidation through `createInvalidator()`—each key is invalidated at most once per 300 ms, so a burst of events triggers only one refetch. See the event table in [API and events](/docs/development-api) for each handler.
- **High-frequency data goes into stores**: `stores/jobs.ts` (jobs and progress), `stores/live.ts` (live state and 10 Hz statistics, `load` = p95 inference time / block length), `stores/train.ts` (up to 20000 metric points per experiment, populated by REST, appended by events, deduplicated by epoch/step).
- **Out-of-order protection**: socket events can race REST snapshots. `isNewer()` in `jobs.ts` orders lifecycle stages (queued/waiting &lt; running &lt; cancelling &lt; finished), never letting jobs move backward; after completion, use `finished_at` to choose the newer snapshot, and during execution, progress within a step only increases. `onFinished` listeners therefore fire once per job.
- **Reconnection**: on `connect`, `resync()` refetches active jobs and live state; on `reconnect`, also invalidate voices, outputs, jobs, assets, experiments, GPU memory, and device lists. This recovers events missed while disconnected.
- **Cross-screen notifications**: when a job started on another screen finishes or fails, `App.vue` shows a snackbar; failures include “Open log”.
- **Preferences** (`stores/preferences.ts`): theme, source color, contrast, language (`auto` follows the system), motion, last screen, last Convert voice, last Separate preset. Stored in localStorage (`rvc-next:preferences`, read by `index.html` and routing before Pinia), and, after loading the server copy, written to `client-state/preferences` with a 500 ms debounce to follow the user across browsers. A `version` field and `merge()` migrate old data (version 2 resets the old stuck reduced-motion preference to follow the system).
- **Deployment root**: `deriveBaseUrl(import.meta.url, origin)` in `api/baseUrl.ts` takes the part of the running script URL before its last `/assets/` as the root, so no API address is compiled into the build; the dev server has no `/assets/`, so the root is the page origin and Vite proxies requests. Scripts from other origins fall back to the page origin.

## Shell, view state, and layout

- **Views stay mounted.** `App.vue` caches views with `<KeepAlive :max="12">`, keyed by destination name, or full path for experiment and voice details (one instance per experiment or voice). Tabs, filters, and forms survive navigating away and back.
- **Scroll positions.** Every page shares the shell's scroller, so `App.vue` records the departing page's `scrollTop` in `beforeEach` and restores it before showing the new view—before the view transition's update callback finishes (`nextTick`), or at `<Transition @enter>` on the fallback path—without jumps. This stays in memory: refreshing resets all views; only preferences persist.
- **One column of sections.** Convert, Separate, Live, voice details, and Models › Tools use vertically stacked sections (`Surface`). Sections widen with the page; internal controls wrap in grids such as `repeat(auto-fill, minmax(min(280px, 100%), 1fr))`, rather than putting sections side by side. Run buttons, jobs started on the screen, and errors sit in the sticky `PageFooter`, always visible regardless of page length. Pages have no `max-width` and fill the content area.
- **Container queries.** `main.content` is the size container `app-content` (`container: app-content / inline-size`). Pages adapt to their actual width (currently, tighter padding at `@container app-content (max-width: 599px)`), rather than window width—rails and side sheets change the available space.
- **Field rows**: rows with a button beside a field (Add, Browse, Build) use `align-items: center` to center the button against the field.
- **Shrinkable names**: audio filenames and voice names are often long unbreakable strings; flex items default to `min-width: auto`, pushing buttons offscreen, so text elements must declare `min-width: 0` to allow ellipsis.

`src/layout.test.ts` checks these rules by reading styles from source files (with explicit file and selector lists). Add new name-bearing rows or section pages to the corresponding list.

## Internationalization

`src/i18n/index.ts` is a small implementation: nested message objects, `t(key, params)` (`{name}` placeholders), fallback to English, then to the key; `tOr(key, fallback)` handles keys built from server values (error codes, stage IDs), showing a readable fallback when no message exists. Languages are `en` and `zh-CN`; with `auto`, `detectLocale()` chooses by browser language (any `zh`/`zh-*` maps to `zh-CN`) and responds to `languagechange`.

`i18n.test.ts` requires identical keys and placeholders in `zh-CN` and `en`, and checks fixed terminology. Device problem messages from the server are in English: the UI translates reason codes and displays server messages unchanged (AGENTS.md §7).

## Adding a screen

1. **API first.** If new endpoints are needed, add them in the core and `api/routers/`, run `python scripts/dev.py typegen`, and alias frequently used schemas in `api/types.ts` (see [API and events](/docs/development-api)).
2. **Queries.** Add keys in `api/queries/keys.ts` and `useQuery`/`useMutation` in `api/queries/<resource>.ts`; job-starting mutations write `Job` to `useJobsStore().upsert(job, '<screen>')`.
3. **Events.** When new or existing events affect new data, write or invalidate the corresponding keys in `api/socket.ts`; put high-frequency data in stores, outside the cache.
4. **Views.** Create `XxxView.vue` in `views/`, add a route in `router.ts`, and set `meta.screen`. For a navigation destination, add an item to `nav` in `App.vue` (using `addressOf()`), and update `SCREENS` in `router.ts` and the list tracking `lastScreen` in `App.vue`.
5. **Composition.** Import primitives only from `@/ui`, favoring unified experience components; use `.sections` with one column of `Surface` sections, actions in `PageFooter`, and `min-width: 0` on text elements in name-bearing rows; add the new file to the corresponding lists in `layout.test.ts`. Use names from `TRANSITIONS`, without literal durations or colors. Add missing primitives to `ui/` and export them from `ui/index.ts`, rather than patching call sites.
6. **Copy.** Add keys to both `i18n/en.ts` and `i18n/zh-CN.ts`.
7. **Checks.** Run `python scripts/dev.py test-web`, then exercise the screen in a browser with `python scripts/dev.py dev`, including narrow screens (&lt; 600 px) and reduced motion; new components can go in `DevComponentsView` to check theme and motion.
