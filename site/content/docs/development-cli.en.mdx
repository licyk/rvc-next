The `rvc-next` CLI is a thin shell over the core: each command parses arguments, calls one core method, and prints a table or JSON. This page explains its organization and the rules for adding commands. See [Command reference](/docs/cli-commands) for each command's options, and [Configuration and environment variables](/docs/cli-config) for settings and environment variables.

## Structure

| File | Responsibility |
| --- | --- |
| [`cli/app.py`](https://github.com/licyk/rvc-next/blob/main/rvc_next/cli/app.py) | `get_app()` registers all commands and groups; `main()` runs the app and handles errors centrally |
| [`cli/factory.py`](https://github.com/licyk/rvc-next/blob/main/rvc_next/cli/factory.py) | `typer_factory()` and custom Typer classes; imports of Typer's private `typer._click` module exist only here |
| `cli/commands/*.py` | Command functions: plain functions without decorators |
| `cli/output.py` | `open_services()`, `print_json()`, `print_table()`, `human_size()`, etc. |
| `cli/params.py` | Voice parameter options (`ParamOptions`) shared by `convert`, `live run`, and `preset save`, plus `build_params()` |
| `cli/progress.py` | Rich progress bars (`job_progress()`) and completion handling (`finish()`) for foreground jobs |

There are two entry points: `[project.scripts]` in `pyproject.toml` maps `rvc-next` to `rvc_next.cli.app:main`, and `rvc_next/__main__.py` makes `python -m rvc_next` call the same `main()` (this is how `dev.py dev` starts the API).

This structure comes from ani2xcur-cli, carried forward through SD Model Hub.

### Central registration

`get_app()` is the CLI's directory: every command is registered here with `app.command(help=..., name=...)(function)`, with its name and help supplied at registration rather than derived from its function name or docstring (`live_test_tone` is registered as `test-tone`, `model_list` as `list`). A command group is another app created by `typer_factory()`, attached with `add_typer(..., name=...)`, at most three levels deep (`model index assign`). Apps are built inside the function; importing the module creates nothing.

The current command tree:

```
rvc-next
├── webui | version | env | doctor | convert | separate
├── config    show | get | set | path
├── assets    list | download | verify
├── model     list | info | import | catalog | download | edit | remove | merge | extract
│   └── index attach | assign | build
├── preset    list | save | remove
├── train     list | new | run | status | export | import
│   └── dataset scan | speakers
├── live      devices | check | test-tone | run
└── jobs      list | show
```

`EXPECTED_TREE` in [`tests/cli/test_cli.py`](https://github.com/licyk/rvc-next/blob/main/tests/cli/test_cli.py) is a snapshot of this tree; `test_command_tree` compares each level. Adding or removing commands without updating it fails the test intentionally: the CLI is a public interface, and changes should be explicit decisions.

### Factory and custom classes

`typer_factory(help)` gives every app and command group the same settings:

| Setting | Effect |
| --- | --- |
| `add_completion=True` | Shell completion support |
| `no_args_is_help=True` | Show help when the app or group is run without arguments |
| `cls=AlphabeticalMixedGroup` | Groups have `--debug` and list commands and subgroups alphabetically |
| `rich_markup_mode=None`, `rich_help_panel=None` | Plain-text help |
| `pretty_exceptions_enable=False` | Leave exception handling to `main()` |

`--debug` is available at every level (`rvc-next --debug version`, `rvc-next model --debug list`, `rvc-next model index --debug --help`), without any command function declaring a `debug` parameter. Three parts implement it:

1. `_make_debug_option()` creates a flag with `is_eager=True`, `expose_value=False`; its callback sets the `rvc_next` logger to `DEBUG`. Eager evaluation makes it apply before the command body; hiding the value keeps it out of command arguments; the callback does nothing when `ctx.resilient_parsing` is true (shell completion).
2. `DebugTyperCommand` and `AlphabeticalMixedGroup` insert this option at the start of the parameter list in `__init__` (without duplicating it if already present).
3. `DebugOptionTyper.command()` defaults to `DebugTyperCommand`; the factory's `cls=` specifies the group class.

`test_debug_everywhere` covers all three positions.

## Errors and exit codes

Domain errors ([`core/errors.py`](https://github.com/licyk/rvc-next/blob/main/rvc_next/core/errors.py)) each carry an `exit_code`; see [Architecture](/docs/development-architecture) for the full mapping. The CLI converts them to exit codes in two places:

- **`DebugTyperCommand.invoke()`** catches `RvcNextError`, logs `e.message`, adds `Install with: rvc-next assets download <ids>` when `detail.assets` is nonempty, then calls `raise typer.Exit(e.exit_code)`. This belongs in the command class as well as `main()` because tests use `typer.testing.CliRunner` to invoke Click commands directly, bypassing `main()`. Tests therefore see the same exit codes as users (`test_missing_asset_exit_code` asserts 7 for missing assets, and 2 for `model info nope`).
- **`main()`** is the fallback: preserve `typer.Exit`, use 1 for `Abort`, display `ClickException` and use its exit code (2 for argument errors), use the code from `RvcNextError`, 130 for `KeyboardInterrupt`, and print a traceback then exit 1 for other exceptions.

Foreground job failures are recorded in `Job.error` rather than raised as exceptions. `finish(job)` in `cli/progress.py` handles completion: return for `completed`; exit 130 for `cancelled`; on failure, print the message and find the error class's exit code by `job.error.code` (3 for `busy`, 4 for `invalid_model`). Thus `rvc-next convert` exits 7 when RMVPE is missing, whether detected during pre-submission validation or job execution.

A few commands choose exit codes themselves, consistently with domain errors: `webui` exits 4 without an access token on a non-loopback address and 3 when no port is available; `model import` prints an ambiguous import plan and exits 3; `live check` / `live run` exit 8 for device problems. CLI-only argument validation uses `typer.BadParameter` (exit code 2).

## Output: `--json` equals API JSON

Every command that lists or displays data has `--json`. `print_json()` serializes `Record` with `model_dump(mode="json")` (recursively handling lists and dictionaries, converting `Path` to strings), so output exactly matches API JSON. This is more than a convention: commands and routes call the same core method and return the same `Record`. `test_model_json_matches_api_shape` directly compares `rvc-next model list --json` with `GET /api/v1/models`.

Without `--json`, `print_table()` renders a Rich table. Logs (including errors) go to **stderr** through `RichHandler` in `rvc_next/logger.py`, while data goes to **stdout**, so logs do not disrupt `rvc-next model list --json | jq`. The default log level is `INFO`, adjustable with `RVC_NEXT_LOG_LEVEL` or `--debug`.

## Services and foreground jobs

Commands obtain services with `with open_services() as services:`. Its call to `build_services()` **starts no background threads**: no scheduler, idle unloading, or Live worker supervision. Services close when the command finishes.

Long operations (conversion, separation, training, downloads, merging, extraction, index building) are core jobs. The CLI calls core methods with `foreground=True`, routing them through `JobService.run_now()`: jobs still enter the database and publish events, but execute **on the calling thread**. Ctrl+C sets the cancellation flag, cancels the engine token, and kills worker subprocesses; the job ends as `cancelled`.

`job_progress(services)` subscribes to the same `job_updated` / `job_log` events as the Web UI, draws a transient Rich progress bar on stderr ("title · current step"), and prints log lines starting with `error` or `Traceback` in red. It shows no bar when stderr is not a terminal or `--json` is used.

Some command-specific behavior:

- **`jobs list` / `jobs show`** read the shared database in the data directory, so they can see a running server's jobs; SQLite WAL and `busy_timeout` make these concurrent reads safe. `jobs show --log` reads job logs in chunks by byte offset. Jobs can only be cancelled through the Web UI or by pressing Ctrl+C in a foreground command.
- **`live run`** starts the same Live worker in the foreground and refreshes a status line four times per second (state, load `infer_ms_p95 / block_ms`, latency, levels), until Ctrl+C, the `--seconds` limit, or an error. Device options `--input`, `--output`, `--monitor` accept a device ID, name, or `default`, resolved against a freshly enumerated device list first.
- **`webui`** starts the server; see the steps below.

### Voice arguments

A voice can be specified by ID, name, or `.pth` path. With a path, `convert` uses `services.models.temporary()` to register a **temporary voice** (`tmp-…`, hidden from lists), with an optional index supplied by `--index`; parameters start from `convert.default_params` rather than the voice's default preset. `live run` only accepts library voices (`resolve(..., allow_path=False)`): `LiveConfig` identifies the voice by ID, saved as `live.last_voice` after startup so the next `live run` without `--voice` and the Web UI can restore the session.

`ParamOptions` in `cli/params.py` defines `--speaker`, `--pitch`, `--formant`, `--f0`, `--index-rate`, `--protect`, `--rms-mix`, with the same ranges as `VoiceParamsModel`. `build_params(base, **overrides)` overlays only user-supplied options on `base` (the voice's default preset, the preset selected by `--preset`, or the last Live parameters), then validates with `VoiceParamsModel`. This matches the Web UI: selecting a voice loads its default preset, so it sounds the same in Convert and Live.

### The `webui` command

`cli/commands/webui.py` is the only CLI file that imports the API layer (inside the function):

1. `--data-dir` sets `RVC_NEXT_DATA_DIR` so subsequently started workers use the same data directory; then call `build_services(start_background=True)`.
2. Warn when the host is not loopback; refuse to start without `server.access_token`, exiting 4.
3. `bind_first_free_port(host, port, strict=...)` **binds the socket first**, trying higher ports when occupied (`--strict-port` fails immediately with exit code 3); warn if the actual port differs from the requested one. Binding rather than attempting a connection removes the gap between checking and actually binding, and detects Windows system-reserved ports.
4. Build the app with `create_app(services, bound_host=..., bound_port=...)`, write `server.json`, print `SERVER_READY url=http://…` to stdout (for launchers and other programs), and open the browser after 0.8 seconds if requested.
5. `uvicorn.Server(...).run(sockets=[sock])` serves on the socket just bound; on exit, delete `server.json` and close services.

See [API and events](/docs/development-api) for details.

## Adding a command

1. **Start with a core method.** If the core lacks a method for the operation, add one to the appropriate service, taking and returning `Record` models. Keep business logic out of commands, or the API and Web UI would each need their own implementation.
2. **Write a plain function in `cli/commands/`**, declaring parameters with `Annotated[..., typer.Option(...)]` / `typer.Argument(...)`, without decorators:

    ```python
    def thing_do(
        target: Annotated[str, typer.Argument(help="Voice id or name")],
        experiment: Annotated[str, typer.Option(help="The experiment to use")],   # Required option: no default
        json_output: Annotated[bool, typer.Option("--json", help="Print JSON")] = False,
    ) -> None:
        """A one-sentence description."""
        from rvc_next.core.things.models import ThingRequest   # Put heavy or optional imports inside functions

        with open_services() as services:
            result = services.things.do(ThingRequest(target=target, experiment=experiment))
            if json_output:
                print_json(result)
                return
            print_table(None, ["Field", "Value"], [...])
    ```

    - **Required options have no default**, and precede parameters with defaults (as Python requires). Do not write `= ...`: Typer treats parameters without defaults as required; `...` is an older form whose type conflicts with the annotation, producing a ty error.
    - Commands listing or displaying data provide `--json` and print the core method's `Record` directly.
    - For long operations, pass `foreground=True` to the core method, wrap it in `with job_progress(services, enabled=not json_output):`, and call `finish(job)` afterward.
    - Raise domain errors directly; `DebugTyperCommand` converts them to exit codes. Use `typer.BadParameter` for CLI-only argument problems.
3. **Register it in `get_app()` in `cli/app.py`**, supplying `name` and `help`; create new command groups with `typer_factory(help=...)` and attach them with `add_typer`.
4. **Update `EXPECTED_TREE` in `tests/cli/test_cli.py`**, and test the command (use the `runner` fixture, which sets the data directory, tiny asset directory, and CPU device through environment variables).
5. Confirm that importing `rvc_next.cli.app` still loads neither torch nor FastAPI (`tests/test_architecture.py` checks this).
6. Add the command to the user documentation's [Command reference](/docs/cli-commands).
