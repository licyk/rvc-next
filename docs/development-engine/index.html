引擎

rvc_next/engine/ 是全部机器学习与数字信号处理代码：设备选择、模型缓存、HuBERT 特征、F0 提取、检索索引、合成器网络、离线转换、流式转换、音频编解码、实时音频设备、人声分离和训练的每个阶段。它不知道应用的存在——不导入 rvc_next.core/api/cli/workers，不导入 pydantic 或任何 Web/命令行框架（由 tests/test_architecture.py 守住，见整体架构）。核心层、worker 子进程和测试都只是它的调用者。

本页按模块讲引擎做了什么、为什么这样做。与原版逐行对照的规则、golden 测试和行为变化见与原版的一致性。

约定

  • 参数是冻结的 dataclass：VoiceParams（engine/convert/params.py）、StreamParams（engine/stream/params.py），以及训练各阶段的 SliceRequest、F0Request、FeatureRequest、TrainRequest、IndexRequest。核心层用 VoiceParamsModel/StreamParamsModel（core/params.py）镜像前两者并加上取值范围；引擎自己不做范围校验。
  • 重依赖在函数内导入：torch、transformers、faiss、av、pymss、sounddevice、parselmouth 都在用到它们的函数里 import，所以 import rvc_next.engine.xxx 很便宜，rvc-next --help 不会加载 torch。例外是移植文件（engine/graph.py、engine/f0/rmvpe.py、engine/f0/fcpe_model.py、engine/audio/sinc_resample.py、engine/audio/denoise.py、engine/models/*.py），它们在模块顶层导入 torch，只能从其他函数里被惰性导入。
  • 异常只有 engine/errors.py 里的几种：EngineError 基类、MissingAssetError（带 assets，资源目录 id 列表）、ModelFormatError、AudioError、Cancelled。核心层在 core/engine_errors.py:map_engine_error() 里把它们映射成领域错误；worker 子进程在 workers/base.py:run_worker() 里把它们变成 error 事件，核心层再用 worker_error() 重建。
  • 取消是协作式的：engine/cancel.py:CancelToken，引擎在分块之间调用 cancel.check()，抛出 Cancelled。子进程里的工作不靠它，取消就是杀进程树。
  • sounddevice 只出现在 engine/audio_io/，pymss 只出现在 engine/separate/（架构测试检查），这样其余引擎代码在没有 PortAudio 或 pymss 的环境里也能导入。

运行时

engine/runtime.py 的 Runtime 持有设备、dtype、CUDA Graph 开关、分块配置和已加载模型的缓存。服务器进程里只有一个（由核心层的 ComputeService 构建），Live worker 子进程和每个训练、分离子进程各建自己的——所以它们的显存彼此独立。

GPU 规则与设备选择

原版在 configs/config.py 导入时就执行 GPU 规则并解析 argparse 参数（CLI 和 VST worker 因此得先清空 sys.argv）。这里它是一个纯函数 choose_device(requested, precision) -> DeviceChoice：

条件（cuda_profile）结果
显存 < 4 GiB 或算力 < 5.3不可用（eligible=False）
算力 6.1（Pascal），或名字含 16xx 且算力 7.5（GTX 16 系）fp32
算力 > 6.1fp16
其余不可用

显存按 total_memory / 1024³ + 0.4 计，与原版一致。requested="auto" 时在可用 CUDA 卡中选 (sm, memory_gb) 最大的一张；没有就试 DirectML（directml_device() 真的跑一次张量运算来确认能用），再退到 CPU。显式的 cuda:N 即使规则会跳过也照用，但只在 fp32；dml、mps 不可用时退回 CPU 并在 reason 里说明。precision 为 fp32/fp16 时覆盖规则（fp16 只对 CUDA 和 XPU 生效）。MPS 只在显式请求时使用，auto 永远不选它。

ROCm 版 torch 上（is_rocm()：torch.version.hip），AMD 显卡是 cuda:N，cuda_profile 跳过 SM 规则（此时的计算能力是 gfx 版本）：至少 4 GiB，fp16。Intel 显卡是 xpu:N（xpu_profile：至少 4 GiB，has_fp16 时 fp16）。一个 torch 构建只带其中一种，所以 gpu_backend()（cuda 或 xpu）和 gpu_profiles() 给出训练中整数 GPU 编号所指的设备；visible_devices_env() 对子进程隐藏其余设备（CUDA_VISIBLE_DEVICES，HIP 也读取它；或 ZE_AFFINITY_MASK）。训练的 autocast 和 GradScaler 在 XPU 上用 xpu，DDP 用 xccl 而不是 gloo。configure_cuda_graph 在 ROCm 下从不开启 CUDA Graph。pymss 不支持 XPU，所以分离在 CPU 上加载、再移动网络，并保持 fp32。

list_devices() 列出全部设备（CPU 在最后），供 GET /compute/devices 和 rvc-next doctor 显示每张卡的规则判定。

以修改时间入键，是为了让覆盖同名文件（重新导出、重新构建索引）自动生效，而不必通知运行时。所有方法都在一把 RLock 下，可以从多个线程调用。

显存释放与 OOM

这两个函数的做法参考 ComfyUI 的 comfy/model_management.py：

  • soft_empty_cache()：先 gc.collect()，然后在 CUDA 上 synchronize → empty_cache → ipc_collect（MPS 上 torch.mps.empty_cache()）。先同步，保证没有内核仍在使用要归还的块。torch 未加载时什么也不做。
  • is_oom(error)：识别 torch.OutOfMemoryError、CUDA 的 AcceleratorError 错误码 2、以及消息里含 "out of memory"/"not enough gpu video memory" 的 RuntimeError/MemoryError（MPS、DirectML）。识别到 CUDA 的异步错误时，会触发一次小运算并同步，把挂起的错误“消化”掉，以免下一次操作继承它。它从 sys.modules 取 torch，不会因为判断错误而导入 torch。

OOM 之后由谁卸载什么，是核心层的策略（release_after_oom），见核心服务。

CUDA Graph

engine/graph.py 照搬原版 tools/cuda_graph.py：每个“所有者”对象（net_g、HuBERT、RMVPE、重采样器……）上挂一个 _GraphCache，按调用点命名空间加上每个输入张量的形状、步长、dtype、设备和 requires_grad 作键。第一次遇到新签名时在侧流上预热三次再捕获；之后回放时把输入复制进静态张量、replay()、克隆输出。捕获失败的签名记入 failures，以后直接走 eager。缓存按 LRU 淘汰，容量来自环境变量 RVC_NEXT_CUDA_GRAPH_MAX_CACHE（默认 8）。get_cuda_graph_stats() 返回捕获、回放、回退、淘汰计数。

与原版的区别只有开关：原版读环境变量 RVC_CUDA_GRAPH，这里由 Runtime 构造时调用 configure_cuda_graph(device, wanted) 设置进程级开关，并且只在设备通过一次捕获—回放探测（detect_cuda_graph_support）后才打开。wanted 来自设置：服务器进程用 compute.cuda_graph_offline（默认关，与原版离线默认一致），Live worker 用 compute.cuda_graph_live（默认开）。训练从不开启。

调用方写法统一为 run_cuda_graph(owner, namespace, fn, *inputs)；开关关闭或输入不在 CUDA 上时它直接调用 fn。由于形状是键的一部分，命名空间里要带上影响形状的参数（例如流式引擎的 rvc-realtime-f0-{skip}-{ret}-{ret2}、离线共振峰的 rvc-synth-f0-formant-{n_res}），否则会误用同一张图。

开启 CUDA Graph 时不调用 emptycache`

离线转换器的 _empty_cache() 只在 CUDA Graph 关闭时调用 torch.cuda.empty_cache()：图捕获的内存池必须保留，归还后回放会失败。这一点与原版 Pipeline 相同。

HuBERT 特征

features/hubert.py 用 transformers 的 HubertModel 加一层 final_proj（HubertModelWithFinalProj），从资源目录 hubert_base/（config.json、preprocessor_config.json、pytorch_model.bin 或 model.safetensors）以 local_files_only=True 加载；缺文件抛 MissingAssetError(["hubert"])。DirectML（设备字符串含 privateuseone）上强制 attn_implementation="eager"，因为 DirectML 不实现 transformers 用的全部 SDPA 内核。

extract_features(model, source, version, padding_mask)：

  • v1：hidden_states[9] 经 final_proj，256 维；
  • v2：last_hidden_state，768 维；
  • 四种（版本 × 有无 mask）各自一个 CUDA Graph 命名空间。

归一化只有一处：normalize_input() 读 preprocessor_config.json 的 do_normalize（requires_normalization()，lru_cache），为真时做 F.layer_norm。原版在训练特征提取里按这个标志归一化、推理里从不归一化，潜在地造成训练/推理不一致；真实资源的 do_normalize 是 false，所以两边都不归一化，结果与原版一致，而训练（train/feature_extract.py）和推理共用这一个函数，以后换资源也不会再分叉。

F0 提取

f0/base.py 定义 F0Provider 协议：compute(x, p_len) 对 16 kHz 音频每 10 ms（160 个采样点）给出一个 Hz 值，清音为 0。原版把移调、清音插值和 256 级量化在离线管线、实时引擎和训练提取里各写了一遍，这里各只有一份：

  • interpolate_unvoiced()：用相邻浊音帧线性插值填补清音帧（离线规则）；
  • shift(f0, semitones)：乘以 2^(semitones/12)；
  • to_coarse()：mel 刻度上量化到合成器音高嵌入读取的 1..255；
  • offline_f0()：计算 → 插值 → 移调 → 量化，返回 (coarse, hz)，即原版 Pipeline.get_f0。

流式引擎因为要在设备上处理张量，有自己的 _get_f0/_f0_post，数学相同（见下文）。训练的 F0 不移调。

方法实现设备资源

rmvpeRmvpeProvider → f0/rmvpe.py:RMVPE（照搬），infer_from_audio(x, thred=0.03)CUDA/CPU 用 PyTorch；DirectML 用 onnxruntime 的 DmlExecutionProviderrmvpe（rmvpe/rmvpe.pt）；DirectML 上 rmvpe-onnx（rmvpe/rmvpe.onnx）

FCPE 的移植

原版通过 torchfcpe.spawn_bundled_infer_model 使用 FCPE。f0/fcpe_model.py 只移植了这一个模型真正走到的路径：Wav2Mel（128 bin log-mel，16 kHz，hop 160）、纯卷积的 CFNaiveMelPE（ConvOnlyEncoder 堆叠 ConformerConvModule）、两种解码器和 load_fcpe()。注意力分支（依赖 einops、local_attention）对 conv_only: true 的 fcpe_c_v001.pt 永远不执行，所以没有移植；非 16 kHz 输入用移植的 sinc_resample.Resample 重采样，与 torchfcpe 使用 torchaudio 时相同。算术未改，输出与 torchfcpe 逐位相同（tests/engine/test_fcpe_model.py）。这样 rvc-next 不再依赖 torchfcpe（它会拉入 torchaudio），权重作为 fcpe 资源下载（来源见资源与模型仓库）。

f0/fcpe.py:FCPEInfer 在此之上处理设备差异：CUDA 且 CUDA Graph 开启时，mel 在图外计算，网络和解码在图内（解码的偏移张量提前放在设备上，因为图捕获禁止主机到设备拷贝）；DirectML 缺少 mel 阶段用的复数 STFT，且 gather 返回错误的 bin，所以 mel 和解码在 CPU、只有网络在 GPU。

检索索引

  • 检索（index/retrieval.py）：load_index() 读 faiss 索引并一次性 reconstruct_n 出全部向量，得到 LoadedIndex(path, index, vectors)；名字含 trained 且同目录有对应 added 文件时换成后者（原版行为）。blend(feats, index, k=8) 用 top-8 近邻按距离平方倒数加权平均。原版每转换一个文件都重新 read_index + reconstruct_n，批量转换很慢；这里由 Runtime.index() 按路径和修改时间缓存。
  • 识别（index/inspect.py）：inspect_index() 以 mmap 方式打开，只读 d 和 ntotal。IndexInfo.version 由维度给出（256 → v1，768 → v2），empty 表示 ntotal == 0，即没有加入向量的 trained_* 索引。导入会话和索引收件箱用它按内容判断索引与音色是否匹配，而不是按文件名。
  • 构建（index/build.py，训练的 index 阶段，移植自 train/train_index.py）：拼接特征、打乱、存 total_fea*.npy；超过 KMEANS_THRESHOLD（200,000）个向量时用 faiss k-means 降到 KMEANS_CENTRES（10,000）个中心（原版用 scikit-learn 的 MiniBatchKMeans，换成 faiss 少一个依赖）；IVF{n},Flat，n = min(16·√N, N/39)，nprobe = 1；先写 trained_IVF…index，再分批 8192 加入向量写 added_IVF…index。多说话人实验（有 multispeaker_manifest.json）每个说话人一个索引，文件名带 _spkid<N>。

索引何时重建

原版只要存在任何 added_*.index 就跳过构建，新数据训练后仍用旧索引。这里每组特征文件的指纹（train/fingerprint.py:of_paths，混入版本和名字）存在 index_fingerprint.json，指纹变了或 force=True 才删掉旧文件重建，否则返回 reused: true。

加载、融合、提取、改信息

  • loader.py:load_voice()：读小模型，把 config[-3]（说话人数）改成 emb_g 的实际行数，构建对应合成器、删除 enc_q、load_state_dict(strict=False)，按精度转半精度或单精度。即原版 VC.get_vc，去掉了返回 Gradio 更新字典的部分。
  • merge.py:merge_models(a, b, dst, alpha=…)：alpha·a + (1−alpha)·b，结果为 fp16。两者的版本、音高引导和采样率必须相同、结构必须一致；emb_g 行数不同时保留较短的（原版规则）；采样率、版本取自 a；speaker_info 只在两者相同时保留。
  • extract.py:extract_small_model()：从 G 检查点提取小模型。config_for(sample_rate, version) 生成原版写入的 18 项配置——v2 的 40k 用 v1 的 40k 布局，与原版 configs/v1/40k.json 一致。
  • checkpoint.py:change_info()：复制一个小模型并改写 info 或说话人名（原版“修改信息”）。音色库把用户改的说话人名存在 voice.json，不改 .pth。

离线转换

convert/offline.py 的 OfflineConverter.convert(audio_16k, voice, params, index=…, resample_to=…, progress=…, cancel=…) 逐行移植原版 infer/vc/pipeline.py，返回 (int16 采样, 采样率)。输入是已经解码成 16 kHz 单声道的 float32（解码由核心层用 audio/io.py:decode 完成）。

flowchart TD
    A[16 kHz 单声道] --> B["prepare_input: 峰值超过 0.95 时缩放"]
    B --> C["highpass_16k: 48 Hz 5 阶 Butterworth, filtfilt"]
    C --> D{"长度超过 x_max?"}
    D -- 是 --> E["每隔 x_center 秒, 在 ±x_query 内找能量最低点作为切点 opt_ts"]
    D -- 否 --> F[整段]
    E --> G["反射填充 x_pad 秒"]
    F --> G
    G --> H["整段一次计算 F0: offline_f0, 移调量 pitch − formant"]
    H --> I["逐块 _vc: HuBERT → 索引融合 → 2× 插值 → protect 混合 → net_g.infer"]
    I --> J["去掉每块两端 x_pad 的输出"]
    J --> K["拼接 → change_rms (rms_mix_rate ≠ 1) → 可选重采样"]
    K --> L["to_int16: 峰值超过 0.99 时归一"]

要点：

  • F0 只算一次，覆盖整个填充后的音频，再按块切片，避免块边界处音高不连续。
  • 索引：index_rate == 0 或没有索引时完全跳过检索。融合在 fp32 下进行（半精度时先转 fp32 再转回），与原版一致。
  • protect：protect < 0.5 且有音高时，把原始特征按 pitchf 混回——浊音帧权重 1、清音帧权重 protect——以保护辅音和呼吸声。0.5 关闭保护。整合包在这一判断之前就插值了清音帧，所以 unvoiced = "original" 时没有任何帧低于 1 Hz，protect 从不生效；"protect"（core 的默认值）改用检测器自己的有声判断作为掩码（由 offline_f0 返回），仍然送入插值后的音高；"zero" 在这些帧保留 0 Hz，与经典 RVC 相同。unvoiced 不是 "original" 时，StreamEngine 也做同样的混合，掩码来自与 cache_pitchf 同步移动的有声缓存（原版实时没有 protect）。
  • 说话人 params.speaker_id 直接作为 sid 传给合成器。
  • 取消与进度：每块之前 cancel.check()，每块之后 progress(n/total)。

离线共振峰偏移

原版只有实时引擎支持共振峰（formant）偏移，这里把实时的方法搬到了离线：

  1. F0 按 pitch − formant 移调（与实时相同）；
  2. factor = 2^(formant/12)，要求合成器生成 n_res = ceil(frames · factor) 帧，并把 NSF 的连续音高 pitchf 乘以 n_res / frames，使生成更长的音频时音高不变；
  3. _formant_resample() 用 upp_res = floor(factor · tgt_sr / 100) 个采样每帧截取，再用 sinc_resample.Resample(upp_res → tgt_sr/100) 压回原长度——时长恢复，频谱包络整体上移 factor。

formant == 0 时 n_res 为 None，走的是原版完全相同的调用，所以默认参数下输出与原版逐位相同。

输出比输入略短

输出可能比输入短至多两个 10 ms 帧，这来自原版逐块 p_len = len // 160 的取整，有意保留以维持逐位一致。

流式引擎

stream/engine.py 的 StreamEngine 是“一块进、一块出、没有 I/O”的实时转换器。数学来自原版 infer/rtrvc.py（RVC.infer）和 realtime_gui.py 的 start_vc、audio_callback；原版这套 DSP 链在 GUI 回调、rtrvc 和 VST worker 里有三份拷贝，这里合为一个类。process() 是同步的、只接受普通数组，所以它可以由 PortAudio 会话驱动、由测试拿 WAV 驱动，也可以在将来由 VST 适配器或浏览器传输驱动。

    A["一块输入 (设备采样率)"] --> B{"threshold_db > −60?"}

  • HuBERT 对整个 context 运行（上下文越长，特征越稳），但检索只处理 skip_head // 2 之后的新帧，生成也只生成新的音频（skip_head/return_length），这是延迟可控的原因。
  • F0 只在缓冲尾部计算：长度 block_frame_16k + 800，RMVPE 时向上取整到 5120 的倍数再减 160（RMVPE 的帧对齐）。结果去掉首尾几帧后滚入 1024 帧的 cache_pitch/cache_pitchf。实时的 pm 与离线不同：两端按 65 Hz 下限补零、截到块的帧数（_pm），这是原版的实时写法。
  • 共振峰：return_length2 = ceil(return_length · factor)，cache_pitchf 乘 return_length2 / return_length，生成后按 upp_res 重采样回来——离线方法就是从这里来的。
  • SOLA（audio/sola.py，来自 DDSP-SVC）：在 sola_search_frame 范围内找与上一块尾部归一化互相关最大的偏移，sin² 淡入淡出，保存下一块要用的尾部。
  • 设备采样率与 16 kHz、合成器采样率与设备采样率之间的重采样都用移植的 sinc_resample.Resample，并走 CUDA Graph（realtime-input-resample、realtime-output-resample）。

与原版的两处不同

  • 说话人生效：原版 rtrvc.py 把 sid 写死为 0，多说话人音色在实时 GUI 和 VST 里无法选人；这里用 params.speaker_id，并钳制到 [0, n_spk−1]。
  • 改块长不重载模型：见下一节。

实时音频设备（audio_io）

原版 realtime_gui.py 的设备处理有一串问题：同一个麦克风按 Windows 每种驱动（MME、DirectSound、WASAPI、WDM-KS）各出现一次，用户必须先选驱动类型；MME 把名字截到 31 个字符，GUI 又按名字保存和匹配；单个双工 sd.Stream 要求输入输出同一驱动类型；保存的设备不在时静默换成系统默认；刷新列表要停止转换并调用私有的 sd._terminate()/sd._initialize()；改任何设备都要停流重载模型。audio_io/ 是对这些问题的重写。

枚举与分组（devices.py）

enumerate_raw() 是唯一导入 sounddevice 的函数：query_hostapis()、query_devices()，并用 check_input_settings/check_output_settings 探测 44.1/48/88.2/96 kHz 是否支持。它在短命的 workers.devices 子进程里运行，所以重新枚举不会扰动正在运行的流。

group_devices() 与 resolve_selection() 都是纯函数，测试用捕获的真实枚举结果（tests/fixtures/devices/{windows,macos,linux_pipewire}.json）驱动：

  • 名字规范化（normalize_name）：大小写折叠、合并空白、去掉某些驱动追加的 (<host api>) 后缀。
  • 按名字从长到短分组，这样 MME 截断到 31 字符的名字可以作为前缀找到同一设备的完整名字；前缀有歧义时单独成组——分错的代价是重复显示，比合错安全。
  • 每组是一个物理设备，variants 按驱动排名排列，第一个是推荐驱动。排名（HOST_API_RANKS，越小越好）：Windows ASIO → WASAPI → WDM-KS → DirectSound → MME；macOS Core Audio；Linux JACK → ALSA → Pulse → OSS。
  • 设备 id 是 sha1(host_api | 原始名字 | 方向 | 同名序号)[:12]，跨枚举稳定；portaudio_index 只在本次枚举内有效，从不保存。
  • Microsoft Sound Mapper、Primary Sound Driver 这类“跟随系统默认”的别名不列出；虚拟设备（VB-Audio、VoiceMeeter、BlackHole、Loopback、Soundflower、null sink……）打上 is_virtual。

resolve_selection(selection, device_list, direction) 在新列表里找回保存的选择，依次尝试：相同 device_id → 相同物理键且同驱动 → 相同物理键的推荐驱动 → 任意驱动上的相同名字 → 系统默认。返回状态 exact、matched、default_fallback 或 missing，后两者带一句说明。是否允许输出回退到默认设备是核心层的决定（allow_output_fallback），因为把转换后的声音送到扬声器而不是虚拟线缆，是用户最先注意到的错误。

会话与拓扑（streams.py）

AudioSession 在一个 Backend 上打开输入、输出和可选的监听输出，用环形缓冲连接，并运行一个处理线程把整块交给处理器（通常是 StreamEngine.process）。

  • 引擎采样率（engine_rate）：输出端选定的采样率；否则输出设备默认采样率（若支持）；否则 48 kHz。这取代了原版用户难以判断的 sr_model/sr_device 开关。
  • 拓扑（choose_topology）：输入输出同一驱动且都支持该采样率时用一个双工流（duplex，延迟最低）；否则输入流 + 输出流（split），中间的环形缓冲带漂移校正。输入设备不支持引擎采样率时以自己的默认采样率打开，用 LinearResampler 线性插值转换——引擎反正要再重采样到 16 kHz，这里线性插值的代价很小。监听输出永远是独立的输出流，由处理线程分出一路（monitor_source：converted、input 或 both）。
  • 声道：输入打开到所选最高声道（默认单声道），回调里把所选声道混成单声道；输出把单声道写到所选声道（默认前两个）。有些驱动不接受比设备本身更少的声道（WDM-KS 的 pin、只支持立体声的声卡），以单声道打开会报 Invalid number of channels [PaErrorCode -9998]。所以枚举时也探测声道数（probe_device：在默认采样率下试 1、2 和最大值，其中有失败时再逐个试到 8），设备拒绝某些声道数时记为 channel_counts。打开流时取不小于所需的下一个可用声道数（accepted_channels），多出的声道不用；支持的采样率也按这个声道数探测。
  • 回调只搬数据和计数，不碰 torch、不写日志、不分配大对象。输出环形缓冲启动时预填一块静音（split 时两块）。
  • 设备丢失：流的 finished_callback 意外触发，或看门狗发现某个角色超过 max(0.5 s, 3 块) 没有回调，即报告丢失（on_device_lost(role, device_id, reason, message)），只报一次。PortAudio 错误文本由 classify_portaudio_error() 归入 missing、busy、channels（-9998，单独列出：换采样率解决不了）、format、permission。
  • 统计：输入/输出峰值与 RMS、推理耗时 p50/p95（最近 50 块）、欠载/过载计数、split 时的漂移 ppm。

Ring（rings.py）是单生产者单消费者的 float32 环形缓冲，锁只覆盖索引运算和两次切片拷贝，所以音频回调等待处理线程的时间不超过一次拷贝；写满算一次过载，读空算欠载。

DriftCorrector（drift.py）解决两个设备时钟永远不完全同步的问题：读端对环形缓冲的填充量做指数平滑；偏离目标超过半块时，每 10 ms 删除或复制一个采样（选在每段 10 ms 中最安静的位置），直到回到目标的 1/8 块以内。目标填充量在前 1 秒后取实测值，因为两个回调的相位决定了填充量稳定在哪里，任何常数都猜不准。真实时钟的漂移是几十 ppm，相当于每秒几个采样，听不出来。

SounddeviceBackend 用 PortAudio（latency="low"，WASAPI 经 WasapiSettings：选了独占就独占，否则共享模式加 auto_convert，由 Windows 转换声道数和采样率——PortAudio 自己只做单声道 ↔ 立体声的转换）；enable_asio 设置 SD_ENABLE_ASIO=1，选用 sounddevice 0.5.1 起在 Windows 上附带的 ASIO 版 PortAudio。fake.py:FakeBackend 模拟设备：每个流一个线程按设备自己的时钟（1 + ppm·1e-6 倍标称速率）调用回调，lose(index) 模拟拔出 USB 设备，refuse 让打开失败，输出被录下来供断言。测试和 worker 请求里的 backend: "fake" 都走它（backend_from_request）。tone.py:chime() 是“测试”按钮播放的提示音。

录制输出设备（capture.py）

PortAudio 无法录制渲染端点：输出设备没有输入声道，按输入打开会报 Invalid number of channels [PaErrorCode -9998]。PortAudio 的 WASAPI 宿主 API 在 2022 年才加入环回设备（每个输出再以 <输出名> [Loopback] 的名字列为输入，用 AUDCLNT_STREAMFLAGS_LOOPBACK 打开），晚于 sounddevice 附带的 19.7.0 DLL；它的 ALSA 宿主 API 也无法指定 PulseAudio 监视器。因此由一个环回提供者负责录制：SoundcardLoopback 基于 SoundCard（≥ 0.4.3，没有声音播放时返回静音而不是阻塞），Windows 上用 WASAPI 环回，PulseAudio/PipeWire 上用监视器源。macOS 没有提供者（Core Audio 的进程 tap 不在 PortAudio 之内），loopback_provider() 会说明这一点，消息进入 DeviceList.errors。

  • 列出：打开 live.show_all_devices 时，枚举会请求环回源（"loopback": true）。add_loopback_sources 把它们作为 Loopback 宿主 API 下的输入设备追加进去，索引为负，带 loopback_source（提供者的 id）和 loopback_of（输出的名称）。本身就是环回的 PortAudio 设备（[Loopback]、Monitor of …，见 devices.loopback_target）直接使用，不再询问提供者。环回输入的物理设备键以 loopback: 开头，不会和同名麦克风合并；设置关闭时核心层会隐藏环回输入。
  • 打开：SounddeviceBackend.open_input 和 check 把带 loopback_source 的端点交给提供者。CaptureStream 在自己的线程里打开、读取（record(None)，到了多少取多少）并关闭录制器（Windows 上处于 COM 多线程单元），等待打开完成，因此拒绝会表现为 DeviceOpenError；start() 之后才调用输入回调，录制器中途失效时报告设备丢失。提供者会转换任意采样率和声道数；choose_topology 总是用 split。
  • 回授：输入的 loopback_of 正是输出或监听设备时，核心层拒绝（feedback，在检查、开始、运行中换设备和监听自己时）；按名称比较，在 Windows 上是精确的。

人声分离

  • 模型表与预设（separate/presets.py）：MODELS 是原版 tools/pymss_webui.py 的 MODEL_SPECS——五个 Roformer 模型（vocals、vocals-aggressive、dereverb、dereverb-aggressive、karaoke），每个有检查点、YAML、主/副输出音轨及其标签、批大小、重叠、大小和 SHA-256。预设本身是数据，放在 core/separation/presets.json：五个单模型预设，加两个链 vocals-clean（vocals → dereverb）和 lead-clean（vocals → karaoke → dereverb）。YAML 随包分发（separate/configs/），只有检查点需要下载；resolve_model() 若在资源目录的 pymss_weights/ 旁找到 YAML 就优先用它，以便直接指向原版安装。
  • 链规划（plan_chain）：每一步分离上一步的主音轨；最后一步的主音轨以预设的 primary_stem 标签写出，其他音轨在预设 stems 列出其标签时写出，每个标签只写一次。输出名 <输入>.<标签>.<格式>，冲突时加 -2、-3。
  • 运行器（separate/runner.py:run_separation）：每个输入以 44.1 kHz 立体声解码一次，按计划逐步分离并写出音轨；模型在一个任务里只加载一次；进度按“已处理音频秒数 / 总秒数 × 步数”计算。PymssSeparator 用 pymss 2.1.7 的 MSSeparator，选项与原版相同；pymss 只认识 cpu/cuda/mps，所以 DirectML 上模型先在 CPU 加载再移到设备（fp16 尝试时转半精度）。
  • DirectML 的 fp16 → fp32 重试：DirectML 先用 fp16；在任何文件成功之前出现可重试的错误（不是内存不足）时抛 RetryInFp32，worker 以退出码 75（EXIT_RETRY）结束，核心层用 precision: "fp32" 在新进程里重跑——与原版的设计相同，因为失败的 DirectML 上下文无法在进程内恢复。
  • 导入检查：workers/separate.py 的 check 动作在 CPU 上加载一次导入的模型，让错误的检查点/YAML 组合在导入时就失败。inspect_config() 用 pymss_core 的 detect_model_type 识别 YAML，custom_model() 为导入的模型生成与 resolve_model() 同形的描述。
  • FakeSeparator 把输入减半作为两个音轨，可配置延迟和 fp16 失败，供测试使用。

训练

核心层在这些阶段之前还有一个可选的 clean 阶段（用分离预设清理数据集），它调用分离服务而不是引擎的训练代码，见核心服务。

每个阶段是一个函数：接收冻结的请求 dataclass，写入实验文件夹，通过回调报告进度和日志，已完成的工作跳过。它们在 workers.train 子进程里运行（每个阶段一个进程，取消即杀进程树）；需要并行的部分由 train/parallel.py:run_parts() 以 spawn 方式启动子进程（fork 会破坏 CUDA 和部分 BLAS），只有一个部分时在本进程内运行。

指纹

train/fingerprint.py:of_paths(paths, extra) 对给定文件和文件夹（递归）的相对名字、大小、修改时间做 SHA-1，extra（采样率、F0 方法等决定输出的设置）以文本混入；缺失的路径与空文件夹哈希不同。只看元数据而不读内容，所以对几 GB 的数据集也是瞬间完成。它有两个用户：索引阶段用它决定是否重建（见上文“检索索引”）；核心层在 experiment.json 里为每个完成的阶段记下指纹。“全部运行”会把存储的指纹与重新计算的指纹比较，不一致的阶段及其后各阶段都重跑；设置修改和上游重跑另外会显式标记过期（见核心服务）。

Worker 子进程的入口

四个 worker 都是 python -m rvc_next.workers.<name> <request.json>，共用 workers/base.py:run_worker()：

  • 把真正的 stdout 复制一份留给事件，再把 fd 1 重定向到 stderr——第三方库 print 的内容就不会混进事件流，而是作为日志文本保留。
  • 事件是带前缀 @rvc 的 JSON 行（protocol/jsonl.py）；没有前缀的行由 parse_line() 当作 info 日志。事件类型在 protocol/messages.py：progress、step、log、metric、output、result、error。
  • rvc_next 日志记录器的输出转成 log 事件；SIGTERM 以退出码 130（EXIT_CANCELLED）结束。
  • 异常映射：Cancelled → 130；MissingAssetError → asset_missing（带 detail.assets）；ModelFormatError → invalid_model；OOM → compute_unavailable（detail.reason = "out_of_memory"）；其他 → internal_error，先把完整回溯作为 log 事件发出。

整体架构

本页给出 RVC Next 的全貌：包结构与分层规则、服务怎样被组装、哪些工作在哪个进程里运行、一个请求从浏览器到引擎再回来的路径，以及贯穿各层的几样基础设施：错误、设置、事件、数据库和数据目录。

核心服务

核心层（rvcnext/core/）是 RVC Next 的全部业务逻辑：任务调度、显存管理、资源下载、音色库与导入、转换、人声分离、训练、实时变声，以及它们共用的设置、事件和数据库。API 与命令行都只是它的薄外壳，引擎（rvcnext/engine/）只被它以函数调用的方式使用，且只在函数内部惰性导入 torch。
